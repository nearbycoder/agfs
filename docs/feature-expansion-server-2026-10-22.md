# Server feature expansion — 2026-10-22

Baseline: `9663bb0` (PR81). This allocation implements exactly **17 new operational capabilities, #88–104**. The preceding 70 performance improvements are not recounted. Tests, migration projections, bounded token selection, queue/GC race fixes and compatibility work are supporting implementation, not additional features. Operations UI belongs to a separate agent.

All routes below are under `/api/v1/platform/operations`. Every handler requires namespace-root `manage` authorization before its first database access. File/subtree operations additionally normalize and authorize their paths. Every query/mutation binds the authenticated namespace owner. No paid service, dependency, auth initialization, deployment configuration or CPU limit was added.

## Durable work and compatibility invariants

The actual request callsite is `server.ts` postprocessing for a successful audited mutation (`response.ok && context.action`). It previously called global dispatch. It now passes the authenticated owner; reads and unsuccessful requests do not trigger that dispatch. A request examines at most 50 index plus 50 webhook candidates for its owner and claims/sends at most 50. The cron dispatcher examines at most 50 global due candidates with indexed continuation; it no longer rebuilds the global outbox with `INSERT SELECT` on each request/turn.

Migration0018 adds projections and triggers without modifying the original source-table column layouts. Existing positional writes remain valid. Index job insertion/deletion/retry, entry change/ownership transfer, webhook delivery state/ownership/deletion, recent metric mutation, thresholds and alert state changes maintain the relevant work/count/dirty-owner projections. The pre-existing job/FTS and upload commit transaction conditions remain in force.

Background dispatch claims source generations with a 60-second recovery lease **before** sending. Failed or ambiguous sends retain work. Queue delivery never deletes `resource_work` merely because a message was acknowledged: source completion triggers retire it. Duplicate/reordered deliveries check generation. Old-format messages without a generation remain accepted and process a current source snapshot; old dead letters can record diagnostics but cannot retire unproven current work. Current dead letters update source state only with an atomic generation guard. Index writes/errors and webhook claims/finalization are also generation guarded, so a change during R2/HTTP work cannot finalize a newer source attempt.

Background and GC cursors freeze each traversal's time boundary. Continuous newer arrivals cannot prevent wrapping back to older paused/renewed items behind the cursor. Fairness is eventual traversal of a finite cycle, not equal per-owner throughput or a fixed completion deadline. An overloaded system still accumulates backlog. Paused candidates require bounded cursor work, so paused backlog is not the same as an empty idle turn.

Health selects at most 100 due dirty owners, claims revisions, reads only their recent metrics and maintained index/webhook totals, then commits alert decisions and revision-qualified continuation. The original 10-minute decision rule (inclusive 11 minute buckets), minimum request count, thresholds, failed-webhook semantics and resolution behavior are preserved. Recent metrics schedule their next decay time; new/resolved alerts can cause an additional dirty turn. Dirty changes during evaluation are never acknowledged away. The dashboard's 1h metrics decay and snooze visibility are computed at read time, independently of new traffic.

One persistent single-row allocator supplies exact monotonic identities for work, health, GC and persisted indexing/background policies. Absent policy revision is zero; first creation, updates and recreation receive distinct positive revisions. It is never reset by cleanup. Delete/recreate and migration backfill therefore cannot reuse an older generation. Each allocation adds a counter update and projection update. A SQL CHECK prevents values above `Number.MAX_SAFE_INTEGER`; allocation at the boundary fails the source transaction instead of silently rounding/wrapping. Tests exercise JSON round-trip at the maximum and atomic refusal beyond it. The counter is an additional write hotspot, not a free mechanism.

## Upload and GC protocol

Abandonment atomically wins only against pending state. Multipart completion atomically claims a matching, unexpired pending/completing reservation before R2 completion. A winning completion prevents abandonment. The direct PUT and multipart finalizers retain the immutable object key captured before writing, then re-read state after R2 settles, including failed writes. Missing/expired/changed reservations requeue that key; pending/completing/committed state is preserved. No path-based deletion or refund occurs.

GC needed additional uncounted hardening. A delete can take effect before a late PUT while its promise resolves afterward. The old collector could then remove the PUT finalizer's newly requeued cleanup intent. The deterministic during-GC test reproduced this failure before the fix.

`resource_object_gc` is an **independent durable intent**, not a cascading child of `object_gc`. Source insert/update triggers create or renew its monotonic generation. Duplicate `queueObject` calls now renew intent. A legacy collector's unqualified `DELETE FROM object_gc` cannot remove this projection. The new collector discovers it even when the legacy queue row/reservation is missing; it eventually retires both records after successful deletion and guarded acknowledgement. Thus mixed-version safety is more than SQL syntax compatibility. The test runs baseline9663bb0's compiled candidate and final DELETE statements around a new late-PUT finalizer.

The collector pages at most 100 intent candidates **before** filtering references, saves durable continuation, then rechecks generation and all existing live/recovery/pin/pending-or-completing-upload references before sending R2 deletes. After R2 succeeds, one transaction deletes usage, legacy queue and independent intent only for the same still-unreferenced generation. Newer intent, partial/batch R2 failure, or failed metadata transaction remains retryable. Reference rows can retain an intent; they do not block traversal of later candidates. A pending intent consumes one projection row per key, with no growing attempt history.

The existing immutable-key rule remains essential: legitimate restoration/publication requires surviving reference or active-upload metadata. No database check can make arbitrary external insertion of a previously unreferenced key atomic with R2 deletion. Likewise these tests establish settled R2/finalizer interleavings; they do not establish distributed atomicity if the process is lost after an external write and before its finalizer persists a renewal. This is an explicit residual cross-service failure boundary for independent review, not a claim of an exactly-once storage transaction.

## R1 review fixes and transport limits

These fixes are uncounted; the allocation remains 17 features. The original independent reproductions were rerun before changes: both first-policy races, both long-path cursor cases, and the expired-pin case failed as reported. The same seven-case independent suite passes after fixes in a disposable copy, with only a synthetic signing-key fixture and output path adapted for the new review contract. Post-fix replay writes only to that disposable directory; baseline repro output remains separate. The original whole-population historical benchmark remains separate.

**Initial policy race.** Policy creation no longer collides with absence revision zero. Insert/update triggers allocate an exact persistent identity; the existing final publication guard remains in force. Regressions cover metadata/one-byte policy creation during R2 reads, concurrent first writers, cached-text reuse, delete/recreate, and the safe-integer boundary. One create plus 999 policy updates measured 1,000 source statements, 3,000 SQLite row changes and 93,006 VM instructions: two additional trigger writes per policy mutation. Storage remains one row per configured owner plus the shared single-row counter. These costs are additional, not downstream read savings.

**Late expiry pages.** The previous tuple continuation rewalked preceding equal-expiry pins (independent reproduction: 13,277 versus 1,102,277 VM instructions for 1k/100k without statistics; 13,495/1,102,495 after statistics in this rerun). Separate bounded branches now seek equal expiry by rowid and later expiry by a single effective lower bound. A `CROSS JOIN` keeps the 51-candidate table outermost before metadata point lookups even without statistics; otherwise SQLite could choose an owner-wide outer scan. Each query returns at most 51 rows, writes zero rows, and performs no R2 or queue operation. The local benchmark uses 1k and 100k owned pins plus the same number of interleaved foreign pins:

**Cursor and HTTP transport.** Cloudflare documents a **16 KB URL limit**; a valid maximum Unicode path can exceed this before adding any cursor. [Official Workers limits](https://developers.cloudflare.com/workers/platform/limits/) (checked 2026-10-22; page updated October 12). GET remains supported for URLs that fit. `POST /index`, `POST /uploads` and `POST /retention/references` accept their corresponding GET request schemas as JSON and return identical results. Clients should use POST for these path-sensitive reads. The POST alternatives use the existing bounded `parseJson` and server pre-parser: **16,384 bytes before JSON parsing**, with existing bounded drain/cancel behavior. Oversize bodies return 413; unsupported content types return 415. They do not set an audit action or trigger background dispatch, and return `Cache-Control: private, no-store`. Normal authentication, namespace-root manage/path checks, token operation accounting and request metrics still apply. Tests preserve an existing single token operation charge for both methods; a read does not refund or double-charge it.

The cursor is a SHA-256 scope identity, two bounded safe-integer positions, and a base64url UTF-16 position. Path positions store the suffix relative to the known requested path. No compression/decompression or data-dependent allocation beyond the explicit cursor cap is used. Producer, schema and decoder share the derived **11,023-character cap**: `64 + 3 + 2*16 + 4*ceil(4096*2/3)`. Hashing scope removes duplicated owner/filter/path text. Scope/path/filter changes are rejected. Prefix plus suffix is bounded by the existing 4,096-code-unit valid UTF-8 path, so generated canonical JSON bodies fit the existing envelope. Arbitrary oversized or excessively escaped input remains subject to that envelope; no promise is made that every schema-valid redundant encoding fits it. The reindex review token has an independent 512-character maximum.

**Reference explanations.** Expired pins are filtered after the bounded candidate page using `expires_at > unixepoch()*1000`, matching GC execution-time eligibility. ## R2 inbox lifecycle, response headers, and bounded cleanup

All changes in this section are **uncounted hardening**; #88–104 remain exactly 17 features. Independent R2 cleared all five R1 findings. Its two inbox failures were reproduced using a disposable copy of the exact independent scripts; the two permanent intended-correctness tests failed before repair. Evidence is `/tmp/agfs-server-r2-repro-20261022/{before.log,before-evidence.json,permanent-before.log}`. The original reviewer artifacts were preserved.

**Source-backed inbox.** `resource_failures` now projects current `index_job_status.attempts>0` and current terminal `webhook_deliveries.status='failed'`, including normal HTTP attempt-eight failure and migration backfill without any dead letter. Success, retry/reset, direct deletion, selected history deletion, hourly expiry and FK cascades remove the projection in the same source transaction. Repeated failure/retry cycles keep at most one current projection row per source, not an accumulating history. Webhook owner/path changes move current failure metadata with that source. The baseline entry-update trigger resets indexing attempts on ownership/path edits, so old index failures clear; a later failure uses the new owner/path.

Legacy `queue_failures` remains the existing diagnostics table. It no longer feeds this private projection: late/stale messages and legacy diagnostic inserts/updates/deletes cannot resurrect absent sources or overwrite a newer owner's current error. Current-generation dead letters project only through their guarded source-state transition. Legacy queue diagnostics' pre-existing retention policy was not expanded. Disabled-hook failures remain visible but cannot be retried until enabled. Retry preserves root/manage, owner, live source, attempts/status and enabled checks; the three-statement per-ID batch clears a selected legacy diagnostic only when its live owned source is ready. No API response shape changed.

Sixteen permanent lifecycle tests exercise real attempt-eight consumption, actual indexing error/success, backfill, repeated retries, selected and actual scheduled cleanup, source/cascade deletion, ownership transfer, legacy writes, old/new generations, deleted/recreated sources and authorization-before-reads. The same point-backed inbox SELECT remains one query/51 rows. First/late/end pages over 1k versus 100k owned rows plus equally many unrelated rows use respectively 744/901/36 VM instructions without ANALYZE and 738/902/37 with ANALYZE, equal at both sizes. A ten-source-operation failure/retry/cleanup fixture measures **73 changes / 3,461 VM instructions**, versus **63 / 2,917** with only the five new failure-maintenance triggers disabled for attribution. That disabled variant is unsafe and is not a rollback option. These are source-write costs, not the complete queue consumer/request cost. A failure generally adds one projection insert/update/delete; a webhook owner/path move can update all affected current failures and is not claimed constant-cost. Existing source-delete projection lookups remain in both attribution variants.

**Operations response contract.** The shared `json()` helper overwrote the attempted private cache directive. The Operations response path now sets `Cache-Control: private, no-store` after constructing the response; the global helper is unchanged. The actual handler test asserts the complete header, and the existing bounded-body, method, GET/POST, read-accounting and authorization tests remain. This is a contract correction, not an additional capability.

**Cleanup protocol.** `cleanup.ts` now delegates to `resource-controls-cleanup.ts`. The real scheduled handler starts eligibility at minute 17 and invokes continuation on other minute turns. There are 19 independent task states with a CHECK-constrained name set, one opaque revision per task, an expiry cutoff, and an exact decimal-text rowid cursor. Each traversal freezes its cutoff; a wrap advances it to current eligibility and revisits unfinished parents/arrivals behind the cursor. Advancing on wrap is essential: one permanent multipart abort failure cannot keep all newer expiries outside an obsolete cutoff forever. New normally later expiries cannot extend the current traversal indefinitely. This is eventual traversal under finite backlog and adequate throughput, not equal per-owner throughput or a completion deadline under overload.

Every candidate read uses an explicit expiry-leading index. Continuation separately caps equal-expiry/rowid and later-expiry branches before their small merge, avoiding the R1 late-page scan. Metadata selection excludes payloads, secrets and snapshot bodies. At most one page and one bounded mutation batch are held at a time. Decimal rowids never round through JS numbers; change-log sequence/watermarks stay in SQL. A regression covers consecutive IDs above `Number.MAX_SAFE_INTEGER`.

A named transaction guard checks the previously read task revision (or its absence) before mutations. Live primary-key/rowid/expiry predicates are repeated inside the batch. Object-intent enqueue, matching pin/recovery/upload retirement, bounded child deletion, watermark advancement or device-token revocation, and cursor advancement commit together. Any later statement failure rolls them all back. Concurrent turns cannot acknowledge a newer task revision; the losing turn leaves progress to its winner. R2 aborts happen before the guarded batch, at most five attempts, serially. A failed abort retains reservation metadata in expired state and advances past it for fair later retry. The guarded transaction marks expired pending/completing rows expired and renews their immutable-key intent even when abort fails; waiting for child pages or abort retries therefore does not keep capacity counted as active. Daily usage is not refunded. A concurrent successful commit or renewed reservation fails the retirement predicate.
