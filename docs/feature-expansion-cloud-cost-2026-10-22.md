## Memory: bounded representations, not a measured heap ceiling

Cloudflare's current [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) specify **128 MB per isolate** (the document uses MB), including JS/Wasm allocations and shared concurrent invocations. Paid HTTP/queue CPU defaults to 30 seconds; HTTP can be configured up to 300 seconds. A cron interval below one hour gets 30 seconds of CPU even when an application branch runs only hourly; wall time is separately capped at 15 minutes. Six simultaneous outgoing connections apply per invocation. The limits page and dedicated [Queues limits](https://developers.cloudflare.com/queues/platform/limits/) are more specific than the pricing page's broad cron/queue maximum wording. No limits should be lowered or raised from Node proxy results.

- Index waves retain up to three decoded strings. Original bodies, UTF-16 strings, a temporary `Uint8Array(max_text_bytes)`, slicing, D1 serialization and runtime buffers may overlap. `search.ts:43–49` bounds re-encoded stored content even when malformed UTF-8 expands to replacement characters; it does not make memory equal to three input sizes. The <=1 MiB field remains below D1's [2,000,000-byte string/row limit](https://developers.cloudflare.com/d1/platform/limits/) with bounded metadata. Existing cached text is not round-tripped into the Worker.
- Server multipart uploads allocate one exact **8 MiB** part buffer (`upload-body.ts:10–27`), plus the current transport chunk, digest/runtime and R2 buffers. They do not buffer a 20 GB file. Several requests in the same isolate can multiply this footprint; client sequential bundles are not global server admission. General SDK uploads can retain 3 parts by default, up to 8 explicitly; `uploadStream` and new bundles use one. Those client buffers are outside Worker memory.
- SDK `readBounded` (`automation-core.ts:74–96`) holds input chunks and allocates a joined byte array before decoding/parsing. Thus a 2 MiB response cap is not a 2 MiB process-memory cap. Inventories/maps, bounded JSON parse/serialization, retained UI state and export previews add copies. Prior-listing WeakRef tests establish reachability only. A producer/runtime can deliver a larger individual chunk before rejection.
- CIMD's 128 KiB body can coexist as collected chunks, `Buffer.concat`, the DO's `arrayBuffer`, and a response body. Four accepted requests keep content buffering small, but runtime/process overhead dominates and is not measured here. Workers heap limits and the container's **256 MiB provisioned memory** are separate resources.

Author index tests report Node heap peaks approximately 20–53 MB and RSS 320–346 MB including SQLite/FTS and synthetic bodies. Neither is a Workers heap measurement, limit breach, or proof of headroom. Browser/client memory work mainly affects their own machines. Release verification should obtain actual Worker memory/CPU distributions and resource-limit outcomes.
